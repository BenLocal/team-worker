# 编码行为准则（Karpathy 防错指南 · 展开）

> 写 / 改 / 审代码的可执行细则；AGENTS.md 顶层只留四条高压线，细则在此。

适用于一切写、改、审代码的场景；琐碎改动可酌情放宽。与「工作区规则」一致，此处展开为可执行细则。

1. **先想后写（不臆测、不藏困惑）**
   - 动手前先显式列出关键假设；不确定就停下来问，别默默猜。
   - 存在多种合理解读时，把选项摆出来让用户拍板，不要静默选一种。
   - 问之前先分清：能跑出来的事实（行为、耗时、输出、格式）自己跑一下看结果，不问用户；只把产品选择和个人偏好交给用户。
   - 有更简单的实现就直说；该 push back 时 push back。
2. **简单优先（够用即止）**
   - 只写解决当前问题所需的最小代码；不加没要求的特性、抽象、可配置项、对不可能场景的防御。
   - 单处使用的逻辑不要提前抽象。写完若发现 200 行能压到 50 行，就重写。
3. **外科手术式改动（只动该动的）**
   - 改既有代码时不顺手「优化」相邻代码、注释、格式；不重构没坏的东西；匹配既有风格哪怕你有别的偏好。
   - 只清理「自己本次改动产生」的孤儿（未用 import / 变量 / 方法）；发现既有死代码只提示、不擅删（除非用户要求）。
   - 自检：每一行改动都能直接追溯到用户的需求。
4. **目标驱动（定义成功标准、循环到验证通过）**
   - 把任务转成可验证目标：「加校验」→「先写非法输入的测试再让其通过」；「修 bug」→「先写复现测试再修」。
   - 多步任务先给简短计划，每步标注验证点（步骤 → 验证：检查项）。

## 完成前先证明它真的能用
- 用真实产物验证：跑一遍功能、读实际的值、看 diff。文件时间戳、子 agent 的自述、「能编译」、缓存的截图都只是间接信号，不算证据。
- 验证失败时先怀疑观察方法（查错了进程、读了缓存、看了旧日志），再怀疑被测的系统。
- 能写成脚本的检查就写成脚本：运行它、保留输出，让别人能重跑，而不是只能信你的话。
- 汇报完成时，说明关键结论的证据到了哪一级，没到第 4 级的明确写「未实测」：
  1. 只是推断；
  2. 指出了具体的 `文件:行`；
  3. 推演过坏情况，确认到不了；
  4. 写脚本或测试调用真实代码验证过；
  5. 在运行中的系统里复现过。

## 修 bug 时只提交有证据支撑的改动
- 「也许有帮助」的防御代码是假设，不是修复，不提交。只提交证据能证明必要的最小改动。
- 证据推翻了某个假设，就把因为这个假设加的改动回退掉，不要留着「以防万一」。
- 有便宜的本地测试路径时，先提交失败的复现测试，再在上面提交修复，让 git 历史里先红后绿。测试要靠大量 mock 或集成环境才能写时，改为附上真实命令前后的输出。
- 两次修复都基于同一个前提、都没通过同一个检查，就先怀疑前提：把它写成一句话，找一个「前提不成立时结果会不同」的观察做一下，验证完再做第三次修复。

## 测试测行为，不测实现
- 用两个假想的改动检验一条测试：把行为改坏（返回错值、漏掉或重复一个副作用），测试必须失败；只改内部实现、外部能观察到的结果不变，测试必须照样通过。前一个不满足的测试什么都没证明，后一个不满足的每次重构都要重写。
- 期望值从需求推出来，不从跑一遍被测代码得到；断言只写接口承诺的内容，不多不少。

## 脚本和命令要能安全重跑
- 会改状态的脚本、命令、循环，写之前回答三个问题：连跑两次会怎样？上次在任意一步崩掉，这次重跑会怎样？最后能不能落到同一个状态？
- 每一步从现有状态推导：读当前状态、和目标比较、只补差异。留下的锁、临时文件、写了一半的记录，下次运行要能认出是过期的，比如先写临时路径再原子重命名。

## 重构前先钉住行为
- 动结构之前，先用特征测试、快照或新旧输出对比，把现有行为钉住；没有覆盖的地方先补上再动。类型检查和 lint 通过不算钉住。
- 每一步都保持行为不变，改完在真实产物上对比新旧输出。
- 改名后专门搜一遍旧名字：字符串、文档、注释、配置、脚本里的引用不会跟着符号一起改。

## 收到评审意见时
评审意见（人写的、其他模型给的）先过滤再动手，每条都给出处理结论：改、驳回并说明原因，或者需要用户决定。
- 「如果这里传 null 会怎样」这类假设，沿调用链确认真的会发生；上游已经校验或类型挡住的，驳回。
- 「换种写法更好」不算问题，除非指出了现在的写法具体会出什么错。
- 建议加抽象、抽函数的，先问这段代码会不会真的出现第二种变化，不会就不加。
- 和仓库现有写法一致的不改：评审者往往只看到了 diff。
- 反过来，多个评审独立提到的、给出了具体执行路径的、涉及安全或正确性的，要认真处理，不要因为改起来麻烦就驳回。

> 《完成前先证明它真的能用》及之后几节借鉴自 [pstack](https://github.com/cursor/plugins/tree/main/pstack) 的 prove-it-works、blast-radius、attack-the-premise、test-behavior-not-implementation、make-operations-idempotent、bug-fix 与 refactoring playbook、interrogate（MIT）。

## 改动落地规则（保证"按原实现方式"）
- 修改前先定位同模块"最近 / 最相似"实现，按同样分层和命名扩展。
- 涉及接口改动时，优先保持返回结构、错误码语义、鉴权方式不变。
- 涉及跨模块调用时，优先走既有公共服务 / 边界，不绕过现有结构直接耦合。
- 除非用户明确要求，不进行大规模重构、批量重命名或架构迁移。
