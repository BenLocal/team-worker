# team-worker 飞书消息接入实施计划

> 本文记录首轮飞书接入计划。后续的原会话答复、路由 Agent 和主动私聊规则见 [现行飞书消息工作流](feishu-messaging-spec.md)。

按 [飞书消息接入规格](feishu-messaging-spec.md) 实施。首轮试点交付双向消息，以及看板左下角「设置」里的「飞书接入」。管理员在看板保存团队群绑定、发送权限和提醒开关。可选事件提醒在基本收发通过验收后接入。

部署方案已改为 `team-workerd` 内置接入。下文的外部适配路径可用于旧环境。现在由 daemon 管理长连接、凭据重载和 SQLite 待发队列，设置页全屏显示。可在看板设置页填写自建应用凭据，也可在 daemon 所在机器上运行 `team-worker chat feishu setup`。对于同一飞书应用，部署时应选择内置或外部实例其中之一。

## 阶段与依赖

| 阶段 | 修改位置 | 交付物 | 前置条件 |
| --- | --- | --- | --- |
| 1. team-worker 接口 | `team-worker` | 只读消息游标、幂等发送、接口文档 | 无 |
| 2. Web 设置与飞书投递 | `team-worker`、`pi-feishu` | 左下角设置入口、配置存储、`/tw send`、提醒和回执队列 | 看板和接入端先约定配置接口，可用模拟接口与阶段 1 并行 |
| 3. 两团队联调与试点 | 两个仓库及测试环境 | 真机验收记录、部署配置、暂停和恢复验证 | 阶段 1、2 通过各自测试 |
| 4. 可选事件提醒 | 两个仓库及试点配置 | 任务完成、Agent 异常和预算事件按团队独立订阅 | 与阶段 1、2 共用日志接口，试点在阶段 3 通过后按需开启 |

## 1. 提供只读游标和幂等发送

1. 在 [消息存储](../internal/store/inbox.go) 增加基于 `events.id` 的游标查询。给 [消息日志接口](../internal/server/server.go) 增加 `cursor=latest` 和 `cursor=<nextCursor>` 两种用法。首次请求只返回日志水位，后续升序取大于游标的记录，用多取一条判断 `hasMore`。客户端按不透明字符串保存游标。未传 `cursor` 的调用继续返回原数组。
2. 在现有发送请求中增加可选 `idempotencyKey`。用 Goose 新增表保存团队、幂等键、规范化的发送参数摘要和原返回消息。查键、写入收件箱和日志、保存结果在同一事务执行。相同请求返回原 `requestId`，同键不同请求返回 HTTP 409。幂等记录保留期覆盖接入端允许重试和恢复的完整窗口。上线前用实际最长停机补发窗口确定保留期，并一起写入两端文档。
3. 团队绑定保存 `createdAt`、绑定编号和日志水位。保存新绑定时取当前水位。恢复同一团队的快照时，在恢复事务中更换绑定编号并记录恢复后的水位。接入端清理旧绑定待发项，从新水位读取，服务端拒绝用旧绑定编号提交的新消息。删除团队时移除绑定，同名团队重建和恢复到另一团队身份时由管理员重新绑定。
4. 更新 [接口参考](reference.md)。测试覆盖旧客户端兼容、空日志起点、多页读取、多个团队并发写入、并发重放、写入成功后响应丢失，以及读日志前后收件箱内容一致。使用旧版本数据库副本验证迁移。

**完成条件**。旧 CLI 继续正常收发消息。同一幂等键重复发送后只产生一条收件箱消息和一条消息日志。新读法能在断点后完整读取且不取走收件箱消息。

## 2. 实现 Web 设置和飞书投递

### 2.1 看板和配置接口

1. 用 daemon 的 SQLite 保存飞书接入配置和配置版本。在现有认证接口下增加读写配置和读取接入状态的操作。写操作用版本校验防止覆盖并发修改。校验团队存在性、群与别名唯一性及授权名单。配置读取响应和日志中均不含密钥。
2. 在 [看板入口](../internal/board/web/src/main.js) 把齿轮「设置」按钮放到左侧栏底部。团队列表独立滚动，按钮在展开和折叠状态都可用。复用看板既有对话框与表单样式，提供「飞书接入」页面，含连接状态、团队绑定、发送名单、提醒类别、正文预览及收发暂停开关。
3. 在 [看板路由](../internal/board/board.go) 通过现有会话和同源保护调用 daemon 配置接口，兼容看板部署路径前缀。保存后先显示已保存版本，接入端回报已应用同一版本后显示「已生效」。接入端离线显示「待生效」。保存报错时保留编辑内容。
4. 用浏览器验收无团队选中、长团队列表、侧栏展开和折叠、反向代理路径、键盘操作、保存后刷新、离线保存和版本冲突。后端测试覆盖未登录与跨站写入被拒、敏感字段不返回。

### 2.2 pi-feishu 命令、队列和提醒

1. 在现有飞书入站分发器 `extensions/feishu/index.ts` 接入 `/tw send`。复用结构化 @、事件身份和原会话回执能力。核对飞书网关何时确认事件，确保路由检查和写入持久队列完成后才确认。命令匹配后由接入模块处理，普通 Pi 会话的配对规则与团队群绑定权限分别判断。
2. 接入端启动后向 daemon 登记应用和租户，读取配置并回报已应用版本与连接状态。用定期刷新处理变更，发送前核对当前绑定、权限和开关，配置不可确认时暂停相关投递。群聊目标从群 ID 解析，私聊目标从团队别名解析。通过 `leadAgentId` 找到 Leader，保存解析后的请求，再用固定桥接身份调用发送接口。
3. 将待发团队消息、回执、外发提醒和游标保存到接入端持久存储。入站去重键由租户、应用和飞书消息 ID 组成。出站同步只读取订阅团队的消息日志，按接收方和类型筛选，在同一事务内推进游标并写入提醒队列。发送时核对原绑定，群改绑后废弃旧绑定的待发项。
4. 复用飞书网关发送。分别记录回执和团队消息的投递状态。飞书返回限流时按群退避，结果未知时按规格的幂等条件决定重试或保留待核对。测试实际网关是否透传发送幂等键和飞书消息 ID。默认通知使用固定模板与看板链接，加入正文预览后覆盖截断和提及转义。
5. 用模拟飞书事件和 team-worker 接口测试授权拒绝、错误团队、未 @、Leader 换人、重复事件、重启恢复、分页补发和改绑。模拟写入成功后断开连接，确认回执与 team-worker 原消息编号一致。保留现有 `/herdr` 和普通聊天的回归用例。

**完成条件**。管理员能从左下角「设置」保存配置，重启后仍可读取。授权用户能在群聊和私聊分别发送给指定团队，回复留在原会话。团队提醒只到绑定群，每个队列项可查询送达、重试、失败或待核对状态。

## 3. 联调、试点与回退

1. 先在隔离环境更新 team-worker，再启动接入端。用测试飞书应用和两个测试群走完整流程，至少包含两个团队同时发消息、无权限私聊、跨群隔离、未授权用户、飞书重推、机器人离线超过一页消息、搬迁群绑定和群移除机器人。用原收件箱回读核对提醒没有取走消息。
2. 真机验收记录 team-worker 消息编号、出入站数量、只读游标和飞书侧截图或消息编号。用一条合成请示核对链接能在看板打开，默认提醒确认只展示摘要字段。用匿名数据和测试账号留证。
3. 管理员确认飞书应用归属，从左下角「设置」配置群 ID、逐团队授权名单和提醒开关。备份 daemon 数据库和接入端持久状态，记录部署和设置版本。先启用一个团队的普通提醒，再开该队的 `/tw send`。用第二队复验独立绑定后再扩大范围。同一飞书应用由一个常驻实例接收消息。
4. 需要回退时先暂停接入端的收消息和发提醒，保留队列，记录待核对项。若需要回退 daemon，先在测试库验证旧二进制能否读取迁移后的数据库，再选用可保留新增消息的恢复办法。恢复接入后用两条新消息验证双向投递，并确认原绑定队列没有转发到新群。

**完成条件**。[规格的验收表](feishu-messaging-spec.md#部署与验收) 中两条基本消息路径全部通过。现场有可复查记录，管理员实测能独立暂停和恢复每个团队的收发。

## 4. 接入可选事件提醒

1. 在 [事件存储](../internal/store/events.go) 将 `TaskCompleted`、`WorkerCrash` 和 `BudgetExceeded` 写入只读事件日志，与状态变更在同一事务提交。复用现有事件 ID 和只读游标，接入端离线期间由 daemon 保留事件。
2. 接入端启用扩展游标读取，按团队提醒开关筛选事件，再进入阶段 2 的发送队列。各聊天适配端通过同一个入口读取事件。
3. 逐项验收按团队开关、同事件重放合并、离线补发和群限流。完成通知用任务状态描述，验收结果来自团队汇报。

## 验证命令

- team-worker 代码修改后运行 `make fmt && make vet && make test`，并发发送和游标读写补跑 `go test -race ./...`。新增接口和迁移按项目代码 checklist 自检。
- 看板变更运行 `make web`，再用构建产物跑 Web 设置验收。
- pi-feishu 代码修改后运行 `npm test`、`npm run typecheck`。两个仓库的自动化通过后，再进行阶段 3 的真实飞书联调。
