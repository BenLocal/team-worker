# team-worker 飞书消息工作流

一个飞书自建应用可以接入多个 team-worker 团队。管理员在看板左下角 **Settings → Feishu integration** 完成首次连接，然后填一次自己的飞书 `open_id`，授权该账号向所有团队发指令。

daemon、路由 Agent 和飞书 API 之间的调用见 [飞书接入调用流程](feishu-call-flow.md)。

## 从飞书发起请求

| 用户操作 | 结果 |
| --- | --- |
| 私聊 `/tw send alpha 请汇报今天的进展` | daemon 检查发送权限，把问题交给 alpha 的当前 Leader |
| 群聊 `@机器人 /tw send alpha 请汇报今天的进展` | 走相同的权限检查与投递流程 |
| 私聊或群内 @机器人后直接描述请求 | 团队助手识别查询、管理操作或发给团队的请求。需要转发且团队不明确时，在原会话追问 |

全局授权使用团队名，适用于现有团队和以后新建的团队。群聊可以从任意群发起，初次请求需要真实 @机器人。清空授权账号并保存会暂停飞书收件。未启用全局授权的旧部署继续应用原先的团队权限。

机器人追问团队时，原发送者可引用这条追问并回复团队别名。如果飞书应用只订阅群里的 @ 消息，引用时也要 @机器人。私聊仅有一条待确认的请求时，可以直接回团队别名。选定后，daemon 将原问题投递给对应 Leader。

飞书显示「已转给团队的 Leader」后，Leader 可以用自己收件箱里的请求编号提交进展或最终结果。

## 查询与管理团队

- 问「看下现在有几个team」会收到当前账号可访问的团队数量和名称。也可以指定团队查询成员或任务。
- 问「demo 现在的状态」会收到团队看板摘要，包括在线人数、正在推进的任务、等待和阻塞情况，以及最近一次完成的任务。
- 其他问题由助手直接回答。问题明确指向有权访问的团队时，助手可参考成员、当前任务及最近几项交付的记录。缺少关键信息时，它会问具体缺哪一项。
- 全局授权的飞书账号可以请求创建团队或派发任务。机器人在原会话的卡片上展示命令参数，由原发送者在 10 分钟内点击「确认执行」。按钮不可用时，可以在同一会话回复 `/tw confirm <确认码>`，群聊用文字确认时需 @机器人。每项操作只接受一次确认。
- 派发任务时可以指定现有成员。省略负责人会创建未指派的任务。创建团队会登记 Leader 成员。
- 团队名中的空格会在确认时显示为连字符，例如 `test team` 会显示为 `test-team`。同时要求更改 Agent 运行方式时，助手会先解释建队和启动成员分别需要什么，等用户明确下一步。

| 操作 | daemon 调用的本地命令 |
| --- | --- |
| 查询团队 | `team-worker team discover`，按发送者权限筛选 |
| 查询指定团队现状 | `team-worker board show`，摘要优先展示进行中、等待和阻塞的任务 |
| 查询成员或任务 | `team-worker team status` 或 `team-worker task list` |
| 创建团队或派发任务 | 确认后调用 `team-worker team spawn-team` 或 `team-worker task create` |

查询和操作结果回复发起消息。使用说明见 [飞书接入调用流程](feishu-call-flow.md#团队助手查询与确认)。

## 回复飞书

Leader 用收到的编号提交材料。默认是最终结果，`--progress` 提交进展。请求来自群聊时，Leader 确认材料可以在发起群公开后使用 `--group-approved`。

```bash
team-worker chat reply alpha <请求编号> --progress "回归正在执行，已经完成第一轮。"
team-worker chat reply alpha <请求编号> --group-approved "回归通过。"
```

路由 Agent 只收到原问题和本次提交的材料。daemon 根据保存的原消息回复飞书 Markdown 卡片，较长的结果用小标题和列表。私聊答复回原私聊，群聊答复引用原群消息。并行请求通过不同编号区分。

daemon 在投递前和发送答案前检查原发送者对团队的权限。权限撤销时，未完成的相关投递停止，管理员可在设置页的 **Blocked Feishu requests** 中查看。提交命令限本机当前 Leader 的 Run。

可随回复提交截图、图表、PDF、Word、Excel 和飞书云文档链接。

```bash
team-worker chat reply demo '<请求编号>' '回归通过，详见报告。' --group-approved \
  --image chart.png --image-reply screenshot.png \
  --file report.pdf --file results.xlsx \
  --doc '验收记录=https://docs.example.com/wiki/example'
```

daemon 上传图片并使用 `image_key` 将预览嵌入摘要卡片，或按 `--image-reply` 单独发图片消息。各文件上传取得 `file_key` 后，每个文件各发一条引用原消息的回复。云文档卡片链接使用原文档的访问权限。路由 Agent 只处理文字材料，附件由 daemon 投递。

路由或摘要排队超过 2 分钟时，机器人提示一次并继续等待。未进入团队的请求保留 24 小时。已经投递给团队的请求仍可按编号提交最终结果。

## 主动私聊提醒

主动提醒沿用部署中已有的订阅和默认收件人。需要调整时，可使用 [聊天配置接口](reference.md#api)，设置默认收件人在当前飞书应用下的 `open_id`。

各团队可分别启用发给 `operator` 的汇报、请示，以及任务完成、Agent 异常和预算提醒。默认内容为摘要和看板链接，可按团队开启正文预览。团队内部消息留在收件箱和看板。延迟和重复事件由持久队列管理，提醒的游标读取不消费原收件箱消息。

切换默认收件人从各队当时的消息水位开始。清空 `open_id` 可暂停主动私聊，按请求编号发出的答复仍回原会话。

## 部署与验证

飞书自建应用启用机器人，通过长连接订阅 `im.message.receive_v1`，配置发送消息、接收私聊和群 @ 所需权限。发送图片和文件还需要「获取与上传图片或文件资源」权限 `im:resource`。同一应用只运行一个事件接收实例。路由 Agent 使用独立模型配置，见 [CLI 和服务接口参考](reference.md#飞书自建应用)。

验收时让同一个测试团队同时收到私聊和群聊请求，提交不同的结果并检查两条回复各自回到原处。再验证重推去重、拒绝未授权发送者、权限撤销后的拦截、路由 Agent 离线时的明确命令、重启恢复和超时。主动提醒用测试团队给 `operator` 发汇报，检查默认收件人私聊和原收件箱。
