# 部署主机 部署
> 在 部署主机 上更新 team-worker 二进制的做法，以及重建容器时的启动循环。

- 2026-11-01：部署主机 的 demo 部署由 `/srv/team-worker/docker-compose.yml` 管理，镜像标签是 `team-worker-local:demo-<提交号>`。更新时只加一层二进制，不重建整个镜像：本地 `./docker/team-worker.sh bins` → `ah cp -r bin/docker prod:/srv/team-worker/build-<提交号>` → 在该目录用 `FROM team-worker-local:demo-<上一版>`、`USER root`、`COPY team-worker team-workerd team-worker-ops /usr/local/bin/`、`USER node` 构建新标签 → 备份并改 compose 的 `image:` → `docker-compose up -d`（部署主机 上是独立的 `docker-compose` v2.29，没有 `docker compose` 子命令）。重建会结束所有 Agent：先**单独**执行 `team-worker --remote prod task list demo`，看过结果再重建，有 in_progress 任务就停下问用户（2026-11-01 把检查和重建写进同一条命令，打断了正在干活的 developer，`dsh tui` 成员的上下文因此丢失）。base 镜像用 `demo-fa98bfc`，避免层叠加。这些步骤已写成 `scripts/deploy-compose.sh --host prod --dir /srv/team-worker --base team-worker-local:demo-fa98bfc --remote prod --team demo`，有 in_progress 任务时它会拒绝重建。
- 2026-10-31：`docker exec` 默认是 root，而 部署主机 容器里 root 的 HOME 就是 node 用户的家目录 → 以 root 执行 `team-worker-ops magpie` 写出的 Magpie `providers.json`、Claude 的 `settings.json` 等变成 root 所有，node 下的 Magpie 读不了，模型网关随之失效，正在跑的 tester 报模型错误后停住 → 进容器操作 node 的文件一律 `docker exec -u node`；`ah cp` 覆盖宿主机文件后属组会变成 root，`magpie-config/` 下的文件要改回 `root:ubuntu`。
- 2026-11-01：重建容器后连续重启约 10 次（`docker inspect` 的 RestartCount 到 10），约 6 分钟后自行稳定 → journal 里每轮都是服务启动的 team-workerd 报 `another team-workerd is already using /home/node/.team-worker`，随后 `The Web board failed to start`，`team-worker.service` 失败，容器退出重启；`team-workerd.log` 里同期每轮都有一个没有 `HTTP API listening` 的 daemon（即被 CLI 自动拉起的，无 `--listen`/`--board`）抢先拿到锁，PID 很小（32、44、67），在容器启动后约 100ms 就出现。10-30 03:55–03:59 的部署日志里有同样的循环，所以不是 0787c1c 引入的。谁在开机最早期调用了 CLI 还没查到：查过 `docker-entrypoint.sh` 的 `team-worker-ops proxy` / `systemd prepare`、ops 的 `leader` 子命令（只连 socket，不会自动启动）和各 systemd unit 的 ExecStart，都不调用 `team-worker` CLI（待验证）。处理：同日在 部署主机 的 compose `environment:` 加了 `TEAM_WORKER_NO_AUTOSTART: '1'`（经 `systemd prepare` 写进 `/run/team-worker/agent.env`，服务、Leader 和成员都继承），容器里只剩入口脚本启动 daemon，之后 03:17 和 03:31 两次开机都没再出现抢锁（journal 里 `another team-workerd` 为 0，RestartCount 不再增加），佐证有效，但只有两次样本；仓库的 Docker 部署未改。重建后用 `docker inspect` 的 RestartCount、`team-worker config health` 和 `agent list` 确认。
- 2026-11-01：加上 `TEAM_WORKER_NO_AUTOSTART` 后重建，容器 4 分钟内重启 18 次，原因不同 → journal 每轮都是 `Magpie setup failed: magpie claude configuration failed with exit code 1`，手动执行得到 `astron's model list has no xopglm52`：`providers.yaml` 的 `claude.model` 指向 astron，而 astron provider 已被用户在 Magpie 面板停用（providers.json 里 `"off": true`），`magpie claude` 失败 → 入口脚本退出 → 服务失败 → 容器重启 → 当场把 `claude.model` 改回 `opencode-go/deepseek-v4.1-flash` 后恢复；随后 273c923 让 `team-worker-ops magpie` 在模型或 effort 设置失败时只打 `warning` 并沿用 Magpie 当前模型，部署后 RestartCount 为 0。以后在 Magpie 面板停用 provider 前，先把 `providers.yaml` 里引用它的模型改掉，否则每次启动都会留一条 warning。
