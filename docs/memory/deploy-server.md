# 部署主机 部署
> 在 部署主机 上更新 team-worker 二进制的做法，以及重建容器时的启动循环。

- 2026-11-01：部署主机 的 demo 部署由 `/srv/team-worker/docker-compose.yml` 管理，镜像标签是 `team-worker-local:demo-<提交号>`。更新时只加一层二进制，不重建整个镜像：本地 `./docker/team-worker.sh bins` → `ah cp -r bin/docker prod:/srv/team-worker/build-<提交号>` → 在该目录用 `FROM team-worker-local:demo-<上一版>`、`USER root`、`COPY team-worker team-workerd team-worker-ops /usr/local/bin/`、`USER node` 构建新标签 → 备份并改 compose 的 `image:` → `docker-compose up -d`（部署主机 上是独立的 `docker-compose` v2.29，没有 `docker compose` 子命令）。重建会结束所有 Agent，先用 `task list` 确认没有进行中的任务。
- 2026-11-01：重建容器后连续重启约 10 次（`docker inspect` 的 RestartCount 到 10），约 6 分钟后自行稳定 → journal 里每轮都是服务启动的 team-workerd 报 `another team-workerd is already using /home/node/.team-worker`，随后 `The Web board failed to start`，`team-worker.service` 失败，容器退出重启；`team-workerd.log` 里同期每轮都有一个没有 `HTTP API listening` 的 daemon（即被 CLI 自动拉起的，无 `--listen`/`--board`）抢先拿到锁，PID 很小（32、44、67），在容器启动后约 100ms 就出现。10-30 03:55–03:59 的部署日志里有同样的循环，所以不是 0787c1c 引入的。谁在开机最早期调用了 CLI 还没查到：查过 `docker-entrypoint.sh` 的 `team-worker-ops proxy` / `systemd prepare`、ops 的 `leader` 子命令（只连 socket，不会自动启动）和各 systemd unit 的 ExecStart，都不调用 `team-worker` CLI（待验证）。处理：同日在 部署主机 的 compose `environment:` 加了 `TEAM_WORKER_NO_AUTOSTART: '1'`（经 `systemd prepare` 写进 `/run/team-worker/agent.env`，服务、Leader 和成员都继承），容器里只剩入口脚本启动 daemon，下次重建生效、效果待验证；仓库的 Docker 部署未改。重建后用 `docker inspect` 的 RestartCount、`team-worker config health` 和 `agent list` 确认。
