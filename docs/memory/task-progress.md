# 长期任务与等待状态
> 对照任务、检查点和消息判断真实进度，避免将长期职责和已交接的旧轮次当成持续执行。

- 2026-11-17：远程团队的七项 `in_progress` 任务中，旧观察任务的 result 已明确归档并指向新轮任务，其检查点也已完成或取消，旧任务状态仍未结束；另有长期探索任务把多个已完成批次累积在一个任务内。核对进度时须分别检查任务验收范围、最新结果、替代任务及未结束检查点，不能用进行中数量推断停滞或并发执行数量。证据：同次只读 `task list`、`checkpoint list` 与 `inbox log` 对照。
- 2026-11-17：同次核查发现，成员已在消息中汇报新提交和下一次检查时间，但任务 result 仍停留在前一日；部分未来检查点已登记，成员明确等待通知。任务 `updatedAt` 与消息活跃度因此给出不同印象，不能单凭任务更新时间认定成员停工。已有检查点完成不代表整个任务验收完成，阶段结果与最终验收须分别记录。

- 2026-11-17：成员进程全部存活，但多数终端已回到输入框；Codex 默认关闭 hooks，使 activity 为空，旧终端卡片又将名下进行中任务统一标为 Working on。进程在线、最后活动上报和任务去向须分别展示；未来检查点不能替代显式等待记录。Leader 的空闲检查也需覆盖团队未分派和去向不明的任务。证据：`internal/model/member_work_test.go`、`internal/server/nudge_test.go`。
- 2026-11-18：同一团队在飞书两次查询状态，Codex 整理的等待数量前后不一致，还把 `follow_up` 当成正在执行。复核看板发现，旧等待说明仍会保留在任务进展中，当前检查点可能已经确认。状态答复按看板的 `executionState` 和检查点现态生成，已确认的检查点只说明有人确认收到，结果仍待提交。回归见 `internal/chat/bridge_test.go`。
